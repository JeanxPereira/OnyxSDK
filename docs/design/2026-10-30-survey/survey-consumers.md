# Survey: how the three consumers use OnyxSDK

Method: read-only. GoWToolkit measured on `git archive origin/main` (extracted to scratchpad/gow) because the local checkout (branch feat/gowr-lod-rig-shaders) is a stale pre-port tree (pins v0.6.0, uses v0.x API, did not compile against any published tag per its own port spec).

## 1. GoWToolkit (primary consumer)

### Linking
- CMakeLists.txt:15-20 (origin/main): FetchContent OnyxSDK, GIT_TAG v1.1.0, ONYX_BUILD_EXAMPLES/TESTS OFF. Comment: "Provides Onyx::Onyx + all transitive deps (imgui_lib, glfw, glm::glm, lz4_lib, glad, miniaudio, implot_lib, imgui_color_text_edit, ffmpeg_lib)".
- cmake/GoWToolkit.cmake: target_link_libraries(GoWToolkit PRIVATE Onyx::Onyx Onyx::CliRender Onyx::Exchange). The aggregate "deliberately leaves out" CliRender/Exchange.
- Pin history: v0.5.3 (local main), v0.6.0 (working-tree edit), v1.1.0 (origin/main). Port design doc (docs/superpowers/specs/2026-08-20-gowtoolkit-onyx-v1-port-design.md): "The app does not currently compile against the version it claims to pin. CMakeLists.txt:17 says GIT_TAG v0.6.0. The code calls SceneData::pbrLayers ... exists in no published Onyx tag ... written against a local OnyxSDK checkout mid-flight, and the pin was never moved." Also "tag v1.1.0 does not exist yet" at design time.
- Repin commits: 5e5dda4 "Repin Onyx to the FetchContent-consumable head", 6a9a980 "Repin Onyx for the container path", 3278f9c "Repin Onyx for the module file table" (pin chased SDK head during port).
- Drags in everything (ImGui+GLFW+glad+GL, Vulkan VkContext, glm, lz4, miniaudio, FFmpeg prebuilt DLLs via ONYX_FFMPEG_DLLS, implot, ImGuiColorTextEdit, fonts). GoW is the one consumer that actually uses most of it (VideoPlayer, AdpcmDecoder/SoundPlayer, TextEditorViewer, Viewport3D).

### Workarounds / friction (quotes)
- Source/cli/CliApp.cpp:22-33: "Onyx ships Onyx::Cli::MakeGltfExportFn for exactly this, and the port design assumed it could be called -- but it cannot: the header declaring it (Onyx/Cli/Gltf.h) is public while its only definition lives in Examples/OnyxCli/Gltf.cpp, which compiles straight into the onyxbox-cli executable and into no library at all. A consumer that includes the header gets a link error ... Reported upstream as an SDK gap".
- Source/main.cpp:19-33: two parallel type catalogs: "Populates the legacy Onyx::GameTypes:: catalog. This is now UNRELATED to how Gow2Module/GowrModule stamp a parsed tree's AssetEntry::typeId ... still required, separately, by the older per-type Onyx::Types::ITypeHandler system ... Retiring that system onto the module/DecoderRegistry contract is out of this phase's scope; until then, both catalogs must be populated." CliApp.cpp repeats: "The modules registered below mint their own, separately".
- Source/core/modules/GowrModule.cpp ~l.120: module-minted types "do not (yet) appear on any AssetEntry the tree actually contains -- WadNodeBuilder still stamps the legacy Onyx::GameTypes::* externs. Reported as a gap in task-2-report.md."
- Source/core/domain/ContainerBridge.h: "Projects a Workspace Document onto the legacy Domain::AssetContainer that the ITypeHandler / ViewerRegistry / parser layers still speak ... the same five-line projection had been written out four separate times ... One of them getting it wrong is not hypothetical: the harness originally hardcoded slot 0 and read a compressed GOWR wad's offsets against the still-compressed bytes." (SDK keeps two container models; consumer bridges them.)
- Source/ui/WadBrowser.cpp:23: "Onyx v1.1 removed AssetEntry::profileTag; role is reclassified on demand from the entry's own name + size via Gowr::Classify()".
- Source/AppRegistration.cpp: hand-rolled `--gui <file> [entry]` open+select+open-viewer (depth-first walk of doc->roots, posts SelectionChanged, opens viewer through ViewerRegistry, a leaked static Subscription and a static s_bridges vector). Comment: "Selecting only fills the Inspector -- the Shell opens a viewer from a double-click, not from the event." The SDK has no "open path, select entry, open viewer" API.
- AppRegistration.cpp: audio volume <-> AppConfig bridge via EventFrameEnd/StartupFinished and a static SoundPlayer::s_volume.
- TextureDecode.cpp:90 "existing drift from an earlier SDK pin".
- tests: test_stubs.cpp, theme_stubs.cpp; theme_contrast_test asserts luminance <= 0.35 where Onyx returns 0.38-0.55: "The app pins colour invariants the engine changed when it gained its Appearance module." Baseline before port: 5/7 tests passing.
- Port design ~l.145: "Deleting 227 lines of duplicated GL context management beats porting it", and a harness that "duplicates ~40 lines of Viewport3D::ResizeFBO because that method is [private]".
- Port commits: fad117b "Delete the headless GL harness and hand the CLI to Onyx"; eee07d6 "Move materials onto TextureRole and the flat texture pool"; d12d31d "Resolve the names the Phase 1 alias sweep never reached"; facfd46 "Restore the three excluded tests and fix the theme diagnosis"; de0600f "fix(gowr): Point the handlers at module type ids so viewers open at all"; b009b86 logging macros; b6af8d4 ByteRange.
- Earlier churn: v0.3.0 panel composition (68251b4), v0.4.0 window chrome+layout (31bec23 "Provide default dock layout after Onyx layout-callback change"), v0.5.0 (914995a local Onyx::Gow WAD dispatch layer, a9e4c7d WadTypeRegistry), v0.5.3, v0.6.0, v1.1. Every minor bump cost a consumer commit; v0.x to v1.1 needed a 3-phase port.
- No private-header includes, no patched SDK files, no copy-pasted SDK code found beyond the above.

## 2. Icon-Composer

Ate 30/09 isto vinha do OnyxSDK inteiro -- tema, settings, registrar, a barra de menus DELE por cima da nossa --, e o editor usava uma fracao e brigava com o resto. ### Pre-30/09 integration
- IC_BUILD_UI "Builds IconComposerKit and the app, which pull the OnyxSDK"; IC_ONYX_SOURCE_DIR hard-coded "D:/CodingProjects/OnyxSDK", else GIT_TAG dddce38 (SHA). ONYX_BUILD_EXAMPLES/TESTS OFF; ONYX_COMPONENT_MEDIA OFF with comment: "The video player is the one switch whose name does not follow the others: ONYX_COMPONENT_MEDIA, not ONYX_BUILD_MEDIA. Measured on dddce38 -- with the wrong name the option is simply never read, and configure spends its time downloading a prebuilt FFmpeg this editor will never link." (SF-Symbols uses the wrong name ONYX_BUILD_MEDIA.)
- CMake-4 escape hatch (CMAKE_POLICY_VERSION_MINIMUM 3.5) because Onyx's pins (GLFW 3.3.9, GLM, lz4) declare minimums below 3.5. Warning-flag stripping: "SYSTEM spares Onyx's HEADERS from this tree's warnings, but its own sources still inherit the directory's compile options: measured, glfw and imgui answer -Wall -Wextra -Wpedantic with ~700 lines of noise".
- Fonts: "Onyx resolves its bundled fonts against the EXECUTABLE's directory ... not against the working directory ... Without it the window still opens, but with the ImGui default font and no SF Symbols." (POST_BUILD copy of ONYX_FONTS_DIR).

## 3. SF-Symbols

### Linking
- Source/viewer/CMakeLists.txt: ONYX_BUILD_MEDIA/EXAMPLES/TESTS OFF ("We want none of its media layer"; per Icon-Composer the real switch is ONYX_COMPONENT_MEDIA, so this was probably a no-op). Two routes: read-only snapshot third_party/OnyxSDK-4632c81 (git archive, gitignored) or FetchContent GIT_TAG 4632c81 ("exact SHA, never a branch"; tag pin-4632c81 pushed 2026-10-01 so clones work). EXCLUDE_FROM_ALL SYSTEM.
- Only the SFSymbols executable links Onyx::Onyx. sf_viewer and sf_tests deliberately do not: "Onyx::Onyx carries opengl32 on Windows and GL dl pthread on Linux as PUBLIC link libraries, so the promise is broken at link time even though no GL function is ever called. It would also put ~60 Onyx translation units, GLFW, ImPlot and ImGuiColorTextEdit on the critical path of sf_tests".
- Pulls "GLFW, Dear ImGui, ImPlot, glad, GLM, lz4 and toml++" and uses ImGui + GLFW only.

### Workarounds (quotes)
- CMake 4: "Onyx pins GLFW 3.3.9, lz4 v1.9.4 and GLM 1.0.1, whose cmake_minimum_required are 3.0, 2.8.6 and 3.2. CMake 4.x refuses compatibility below 3.5 outright ... FATAL_ERROR without the escape hatch".
- SDK bug: "FINDING, and it is a bug report for OnyxSDK rather than a patch to the snapshot. 4632c81 lists Source/Services/SessionLog.cpp in ONYX_CORE_SOURCES, and THAT FILE IS NOT IN THE COMMIT ... neither would a git clone of the SHA". Worked around by editing Onyx_Core's SOURCES property (list(REMOVE_ITEM), set_target_properties) with a FATAL_ERROR guard; first version keyed on an empty variable and silently failed ("CORRECTED after review (I2)").
- mingw-w64: 8284988 "Onyx's dark title bar does not compile under mingw-w64" (DWMWA_USE_IMMERSIVE_DARK_MODE); probe+define later removed when the SDK added the guard.
- Warnings leak into the Onyx tree: "thousands of diagnostics about code this repository does not own and may not edit", so warnings moved to per-target.
- "imgui_lib is Onyx's target and it PUBLIC-links glfw and glad ... Building our own ImGui target from the same sources would be the tidier line on paper and a duplicate-symbol link error in SFSymbols".
- Clipboard.h: "neither GLFW nor Onyx adds an image clipboard"; "There is no file dialog: Onyx does not provide" one. Toolbar.cpp: needs imgui_stdlib.cpp, which Onyx's imgui_lib does not compile.
- Window.cpp:48-58 (decisive, 2026-10-01): "Until 2026-10-01 it ran Onyx::App::Window, and the window showed it (laudo 2026-10-01 2.1): Onyx's own menu bar (File / Export / Options / View) above ours, its dock tab headers over each of our panels, and its 'Viewer' and 'Log' panels beside them. None of that can be turned off from outside -- App::frame draws its menu bar, its dock space and its document window unconditionally, App::drawMenuItems is private, and the snapshot under third_party/ is read-only. So the window loop is OURS now: GLFW, the two Dear ImGui backends Onyx's imgui_lib already compiles, and drawChrome (Shell.h) for the frame." Commit a8bc011 says the same.

### What it uses now / fit
Three small services in two TUs: Onyx::Frame::BeginFrame/RequestRedraw (FrameScheduler.h), Onyx::Threading::MarkMainThread, Onyx::Platform::DetectSystemAppearance (SystemTheme.h), plus Onyx's compiled imgui_lib/glfw/glad. Window.cpp 381 + main.cpp 268 lines out of ~27k. Poor fit: a symbol catalog browser with its own chrome has no use for a game-asset shell, VFS, module system or renderer. Same trajectory as Icon-Composer, a day after Icon-Composer's removal: adopted the SDK for the shell (M2b plan: "the viewer builds on OnyxSDK, with the media layer off"), dropped the shell within ~1 month (2026-08-28 to 2026-10-01), kept the dependency only for an ImGui build target and 3 trivial services.

## Cross-consumer findings
1. Two of three consumers ejected the app shell (App/Window) for the same reason: it draws its own menu bar, dock and panels, plus File>Exit calling exit(0), and a host cannot turn them off. Only after the owner added host hooks (File>Open handler, menu filter, Viewer visibility) was it tolerable, and Icon-Composer still left.
2. Dependency weight: every consumer inherits GLFW/ImGui/glad/implot/ColorTextEdit/lz4/glm/toml++. CMake 4 incompatibility (old GLFW/lz4/GLM pins) hit both non-GoW consumers. Opt-out flag names learnt by measurement (ONYX_COMPONENT_MEDIA vs ONYX_BUILD_MEDIA). Onyx::Onyx links GL PUBLIC, which blocks headless tests if linked. Its third-party warnings leak into consumers.
3. Renderer: Vulkan/volk's process-global dispatch table is overwritten by Onyx's VkContext (VkContext.cpp:362); a host with its own Vulkan silently renders on the wrong device. Icon-Composer needed four commits to cope.
4. Packaging bugs: untracked SessionLog.cpp listed in ONYX_CORE_SOURCES at 4632c81; public header Cli/Gltf.h with its definition only in an Example (link error); v0.6.0 tag did not match the code the app used; v1.1.0 tag did not exist when the port was designed; fonts resolved against the exe dir.
5. API churn: GoWToolkit absorbed v0.3, v0.4, v0.5.0, v0.5.3, v0.6.0, v1.1 (ProfileManager to IGameModule/Workspace, ByteRange, TypeRoles, logging macros). Two parallel type models (Types::ITypeHandler + GameTypes externs vs module TypeRegistrar) and two container models (Domain::AssetContainer vs Workspace Document) survive in v1.1 and the consumer writes bridges.
6. Evidence the SDK works where it works: GoW CLI shrank 1,055 to 169 lines via Onyx::Cli::Run; the GL harness was deleted; 83% of GoW code is format knowledge. The data/format/CLI side delivers. The shell, renderer and build/dependency packaging are what consumers reject. The only complete consumer is the author's own GoW app.
