# glTF export — Blender validation (PENDING A HUMAN)

Spec §9's reason for glTF as v1's one interchange format: "glTF opened in
Blender is an *external* oracle for skinning, weights and tangents —
validation not written by us, independent of our renderer." Everything
this SDK has proven about skinning so far was proven against artifacts it
produced itself (the Vulkan/GL parity gate, the oracle corpus PNGs below).
This document is the checklist for the first check by something we did not
write.

**Status: PENDING A HUMAN.** Nothing in this repository has run Blender.
The machine check (`ctest -R OnyxGltf`, doctest cases prefixed
`GltfExport:`) parses the exported files back through cgltf and asserts
counts, accessor min/max, and inverse-bind-matrix alignment — that proves
the files are *structurally* valid glTF. It does not, and cannot, prove
they *look right* to a human eye in Blender. Do not read a green
`OnyxGltf` as this checklist having been done.

## Files to open

Generated by `ctest -R OnyxGltf` (specifically the `GltfExport: human
validation fixtures land in build/gltf-check` doctest case, which
regenerates them on every run) at:

- `build/gltf-check/skinned-cube.glb`
- `build/gltf-check/joint-chain-200.glb`

Both are self-contained `.glb` (binary glTF — geometry, skin, and the
embedded diffuse-checker PNG texture in one file). Drag either straight
into Blender (File → Import → glTF 2.0, or drag-and-drop if your Blender
build supports it).

## skinned-cube.glb

Source: `Onyx::OracleTool::BuildSkinnedCube()` (`Tools/OnyxOracle/
CorpusScenes.cpp`) — a 3-joint chain, one mesh part (`cube_body`, 40
vertices, 60 triangles per `Tests/Golden/corpus/skinned-cube.json`), an
orange/white checker diffuse texture. Bind pose is a straight vertical
chain; rest pose bends joints 1 and 2 by +30° about X (joint 0, the root,
stays unbent) — the corpus PNG at `Tests/Golden/corpus/skinned-cube.png`
is the Vulkan renderer's own picture of that exact rest pose, orange/white
checker cube bending partway up its height, viewed from roughly (4, -6, 2)
looking at (0, 0, 1.5).

Checklist:

- [ ] **Skin binds to 3 joints.** Object Properties → Armature Deform
  modifier (or the Armature data itself) shows exactly 3 bones. In the
  Outliner, the armature has one root bone with a single child, which has
  a single child of its own — a straight chain, not a branch.
- [ ] **Rest pose matches the corpus PNG.** With no pose applied (Rest
  Position, not Pose Position, in Blender's Armature properties), the mesh
  should already be bent — NOT a straight vertical box. The bend should
  visually match `Tests/Golden/corpus/skinned-cube.png`: unbent from the
  base up through the first third, then curving over roughly 60° of total
  bend (30° at each of the two upper joints) toward the top.
- [ ] **No detached vertices.** The mesh reads as one continuous solid
  (a slightly tapered, bent box with distinct rings) — no vertices left
  behind at the old straight-chain bind-pose position, no visible seam or
  gap at either joint. If a chunk of geometry stays straight while the
  rest bends, that is a weight-painting bug worth chasing, not something
  to wave past.
- [ ] **Normals point outward.** Enable backface culling (or check normals
  via the mesh overlay's "Normals" display) — every face should shade as
  the *outside* of the box, not the inside. The box should look solid and
  correctly lit from any orbit angle, not like a hollow shell viewed from
  inside.
- [ ] **Texture is bound and checkered.** The material's Base Color should
  show the orange/white checker pattern (embedded PNG, no missing-texture
  pink/magenta).
- [ ] **Weight painting is smooth across the two bent joints**, not a hard
  cut — Weight Paint mode on the armature's second and third bones should
  show a gradient blend near each joint, not a sharp boundary (the corpus
  builder blends each vertex's weight by inverse distance to its two
  nearest joints — see `CorpusScenes.cpp`'s `BuildSkinnedCube`).

## joint-chain-200.glb

Source: `Onyx::OracleTool::BuildJointChain200()` — 200 single-joint
segments, each its own mesh primitive rigidly bound to exactly one joint
(no blended weights here, unlike the cube above), spiraling by 0.32 units
and yawing 7° per step. From the corpus camera (`Tests/Golden/corpus/
joint-chain-200.png`) the 200-segment spiral reads edge-on as a tight
coiled ring of yellow segments.

Checklist:

- [ ] **200 joints, one straight parent chain.** The armature has 200
  bones, each with exactly one child (the next segment) — not a
  200-bone star or any branching. `ctest`'s machine check already confirms
  the *count*; this step confirms the *shape* (a chain, matching
  `ObjectData::Joint::parent` — segment *k*'s parent is segment *k-1*).
- [ ] **Rest pose is a spiral, not a straight rod.** With no pose applied,
  the 200 segments should curl into a spiral/coil shape resembling
  `Tests/Golden/corpus/joint-chain-200.png`'s tight ring silhouette, not
  lie in a straight line.
- [ ] **No detached segments.** All 200 little boxes should sit end-to-end
  along the spiral with no segment left behind at the origin or floating
  off in the wrong direction — a single misregistered joint here would be
  easy to miss at a glance given the segment count, so scrub slowly along
  the spiral's length at least once.
- [ ] **Normals point outward** on the segment boxes, same check as above.
- [ ] **Performance sanity**: Blender should handle 200 joints without
  complaint. If the import is unreasonably slow or the outliner chokes,
  that is worth noting even though it is not a correctness bug.

## What this checklist is not

It does not check blend modes (Additive/Subtractive have no glTF core
equivalent — see `Include/Onyx/Exchange/GltfExport.h`'s role-mapping
writeup — so `blend-stack` was deliberately not chosen as a fixture here),
does not check UV1 or vertex color (not exported in v1 — see the same
header), and does not check animation playback (`ObjectData`'s animation
clips are a separate v1.1 concern per spec §9, and this exporter only
emits the rest-pose node hierarchy + skin, not any `AnimationData`
clips as glTF animations).
